# AI-ассистент: результаты спайка моделей (фаза 1)

Дата: 2026-10-13. Харнесс: `scripts/ai-spike/` (`node scripts/ai-spike/run.mjs --model <m> --mode tools|format --runs 3 --retry`). Самотест оценщика: `node scripts/ai-spike/score.mjs`.

## Метод

- 10 эталонных русских запросов (`cases.mjs`): создание задачи (абсолютные и относительные даты), массовый сдвиг дат, массовая смена статуса, переименование и удаление проекта, удаление задачи, создание из контекста экрана, неоднозначный запрос, вопрос о данных. Кейсы 8–10 (screen-context, ambiguous, data-question) не использовались при настройке промпта.
- Фикстуры: 4 проекта (включая «KYC Legacy» — похожее название), 14 задач, фиксированная «сегодня» = 2026-10-13. Весь контекст передаётся в промпте; read-инструменты не тестировались.
- Модель возвращает **токены** (`today`, `+1w`, `5d`) и названия/id; даты считает и имена резолвит приложение (`score.mjs`, дни/недели/месяцы — как в `TaskEditView.tsx:191-196`).
- Оценка по **эффектам**: план раскладывается на изменения отдельных сущностей, поэтому «одно действие на три задачи» и «три действия» равнозначны. Неизвестный id/название — ошибка, ничего не «чинится». Единственная терпимость: поля `null`/`""` отбрасываются.
- 3 прогона на кейс (30 на модель и механизм), температура 0.2, `num_ctx` 16384, `stream: false`. Колонка «retry» — доля планов, прошедших после одного повторного запроса с текстом ошибки валидации.
- Механизмы: **tools** — по инструменту на действие; **format** — один JSON по схеме через `format`. Схема дополнительно описана в промпте (см. «Находки харнесса»).

## Находки харнесса (важно для фаз 2–4)

1. **С `format` модель не видит схему.** Ограничение работает только на декодирование. Первый прогон `gpt-oss` без описания схемы в промпте дал 2/10: модель придумала свои типы действий. После добавления схемы и списка типов в промпт — 10/10. Контракт провайдера: схема всегда дублируется в системном промпте.
2. **«Никогда не выдумывай id» нужно ограничивать существующими сущностями.** Иначе модель просит у пользователя id для *новой* задачи. Правило: «для новых задач и проектов id не нужен».
3. **`format` не гарантирован на всех моделях/маршрутах.** `gemma4:31b-cloud` его не соблюдает. Нельзя полагаться на «валидный JSON на выходе» — нужен терпимый извлекатель (вырезать ограждение) плюс валидация и повтор.
4. Модели с `thinking` на локальном железе медленные (`gemma4:e2b` ≈ 29 с на ответ). Нужен индикатор и кнопка отмены (уже в рисках PRD).

## Решение (рекомендация — на подтверждение владельцу продукта)

**Механизм: один JSON-план через `format`** (`{ reply, actions[] }`), а не tool calling.

Обоснование: на целевой модели `format` 30/30 против 27/30 у tools; один объект даёт `reply` для уточнений и ответов на вопросы в том же ответе; один путь кода в провайдере и тот же контракт для других провайдеров позже. Но разница с tools на целевой модели статистически невелика (30 запусков, 3 ошибки tools — одна и та же причина), и tools лучше переносится между моделями: ≥90% с первой попытки на обеих крупных моделях, без парсинга текста.

Условия, при которых рекомендация держится:
- извлекатель JSON терпим к markdown-ограждению (иначе у gemma 0%);
- валидация на стороне приложения + **один** повтор с текстом ошибки (поднимает gemma4:31b format 0% → 83%, gpt-oss tools 90% → 100%);
- схема дублируется в промпте.

Если владелец предпочтёт tool calling — контракт тот же (имена действий и поля совпадают 1:1, см. `ACTIONS` в `run.mjs`), меняется только слой провайдера. Обе ветки прошли целевой порог.

### Контракт плана для фаз 2–3

Источник правды — `ACTIONS` и `P` в `scripts/ai-spike/run.mjs`, нормализация — `score.mjs`.

- Объект: `{ reply: string, actions: Action[] }`; пустой `actions` + непустой `reply` = уточнение или ответ на вопрос.
- Действия: `create_task`, `update_tasks` (`filter` + `set`), `delete_tasks` (`ids`), `create_project`, `rename_project`, `delete_project`.
- Даты: `today`, `±Nd`, `±Nw`, `±Nm`, `YYYY-MM-DD`. Длительность: `Nd`, `Nw`, `Nm`. Сдвиг существующих задач — `set.shift`.
- Проекты — по названию или id; существующие задачи — только по id из контекста; неизвестное → ошибка валидации, не выполнение.
- Валидатор (`validateAction`) и резолвер (`resolveDate`, `resolveDuration`) из `score.mjs` — готовая основа для реестра действий фазы 3.

## Малые модели

- Образцы: `gemma4:e2b` (5.1B, замена «gemma 4 4B» — 4B-тега локально нет) и `llama3.2:3b`. Результаты 40–70% с первой попытки и почти без выигрыша от повтора. Кейсы с несколькими сущностями и вопросы о данных не работают.
- Крупные модели (31B и 117B) — ≥90% первой попытки при корректной обработке формата.
- **Порог предупреждения ~20B из PRD** согласуется с данными, но данных между 5B и 31B нет. Предупреждать по `details.parameter_size` < 20B; точный порог можно уточнить, проверив модель в диапазоне 8–20B.

## Ограничения спайка

- 10 кейсов × 3 прогона: достаточно, чтобы отсечь плохие варианты, недостаточно, чтобы различать 90% и 100%. Метрика «≥80% на gpt-oss» выполнена с запасом, но на малой выборке и маленьких фикстурах (14 задач). Реальные базы больше — контекст придётся ограничивать (read-инструменты, фаза 3/4).
- Не проверялись: многошаговый диалог, read-инструменты, режим Ollama Cloud с API-ключом напрямую, поведение с `plannedStartDate`/`plannedDuration` (правило для сдвига плановых дат ещё надо зафиксировать в фазе 3).
- Все прогоны — через локальный демон Ollama (облачные модели — через `ollama signin`); CORS и сборка Electron не тестировались (фаза 2).
